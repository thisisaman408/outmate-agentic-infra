 1. OVERVIEW & PRODUCT GOALS
================================================================================

Outmate Visitor Tracker is a B2B deanonymisation and intent-scoring platform.
When a prospect browses a customer's website, the tracker:

  1. Captures the visit event via a lightweight JS pixel (<4 KB)
  2. Identifies the visitor's company from their IP address using a multi-source
     enrichment waterfall (PTR, ip-api, IPinfo, Enrich.so, Explorium, RDAP)
  3. Scores their buying intent based on page visited and behavioural signals
  4. Predicts their job persona (engineering / sales / executive / marketing / HR)
  5. Pushes the enriched record to the customer's dashboard in real-time via SSE
  6. Fires webhooks to CRM / Slack integrations when high-value triggers match

Key differentiators vs rb2b / warmly.ai:
  - Free-tier IP identification via PTR + ip-api + RDAP (zero cost per visit)
  - Explorium for full firmographic depth: revenue, funding, tech-stack, LinkedIn URL
  - Cross-org fingerprint identity graph (one visitor re-identified across all orgs)
  - GDPR-compliant consent gate in pixel.js (TCF 2.0, Cookiebot, OneTrust, DNT, GPC)
  - Retroactive backfill: when a visitor submits an email, ALL prior anonymous
    visits are patched with their full identity
  - Account-level intent scoring aggregated across all employees from same company

================================================================================
 3. END-TO-END DATA FLOW
================================================================================

PIXEL LOAD:
  1. Customer embeds: <script src="https://app.outmate.ai/api/v1/visitors/pixel.js"
                               data-pixel-key="pk_..."></script>
  2. pixel.js runs _isConsentDenied() — checks DNT, GPC, Cookiebot, OneTrust.
     If TCF 2.0 CMP present, defers until Purpose 1+7 consented.
  3. pixel.js collects: url, referrer, visitor_id (localStorage UUID), browser
     fingerprint (cyrb53 hash of canvas + WebGL + screen + timezone + UA + etc.),
     page_title, page_h1, connection_type, viewport, scroll_depth, cta_clicks.
  4. Sends POST to /api/v1/visitors/track via sendBeacon (or fetch fallback).

TRACK ENDPOINT:
  5. Next.js proxy route forwards to FastAPI /api/v1/visitors/track.
  6. FastAPI resolves real IP: cf-connecting-ip → x-real-ip → x-forwarded-for
  7. Validates pixel_key against SiteConfig (DB lookup, ~2ms)
  8. Rate limit check: 30 req/min per IP, 1000/min per pixel_key (Redis)
  9. Deduplication: fingerprint window = 4× normal window (longer dedup for same
     browser across pages); IP+domain window for non-fingerprinted requests.
  10. Queues Celery task process_visitor_task with full payload.
      Fallback: asyncio.create_task() if Celery unavailable.
  11. Updates Redis sorted set outmate:visitors:active:{org_id} (30-min window)
  12. Returns {"status": "queued"} in <50ms (non-blocking).

CELERY ENRICHMENT:
  13. Creates stub Visit row (enrichment_status="processing") for UI spinner.
  14. Calls VisitorEnricher.enrich_ip() — full pipeline (see Section 5).
  15. Calls predict_persona() — behavioral scoring on last 30 visits.
  16. Calculates ICP score (0–100) from enrichment completeness + org ICP filters.
  17. Calls _categorize_and_attach() — matches to known company/prospect records.
  18. Runs retroactive backfill if visitor submitted email for first time.
  19. Updates Visit row with full resolution JSONB.
  20. Publishes enriched record to Redis channel visitors:{org_id}.
  21. Fires webhook if alert rules match.

REAL-TIME DASHBOARD:
  22. Frontend calls POST /sse-token → gets opaque 64-char token (60s TTL, Redis).
  23. Frontend opens EventSource(/stream?token=...) → FastAPI SSE endpoint.
  24. SSE handler validates exchange token from Redis (single-use, deletes on use).
  25. Subscribes to Redis PubSub channel visitors:{org_id}.
  26. New visits appear in dashboard table within ~500ms of page load.
  27. Heartbeat ": heartbeat" sent every 15s to prevent proxy timeouts.

================================================================================
 5. ENRICHMENT PIPELINE (STEP-BY-STEP)
================================================================================

ENTRY: VisitorEnricher.enrich_ip(ip, url, intent_score, email, visitor_id, fp)

Private IP check → returns early (no external lookups for 127.x, 10.x, 192.168.x)

Bot pre-filter:
  - Missing UA: +30 score
  - Bot keyword in UA (bot/crawler/spider/headless): +50 score
  - Zero viewport: +30 score
  - If bot_score ≥ 50: return tier="noise" immediately

────────────────────────────────────────────────────────────────────────────────
STEP -1: IDENTITY GRAPH LOOKUP
────────────────────────────────────────────────────────────────────────────────
Five-level cascade (most-specific to least):
  1. visitor_id exact match (most precise — same localStorage UUID)
  2. Cross-org fingerprint: expression index on raw_data->>'fingerprint'
     (same browser seen on ANY org's pixel → instant re-identification)
  3. /24 subnet match: IPs in same /24 block share company data
     (corporate NAT — entire office egresses through same block)
  4. Exact IP match
  5. Email match (if email provided)

Cache sets confidence=0.85 if hit. Merges: full_name, phone, linkedin_url,
job_title, email, company, domain into resolution.

────────────────────────────────────────────────────────────────────────────────
STEP -0.5: PTR REVERSE DNS (FREE)
────────────────────────────────────────────────────────────────────────────────
socket.gethostbyaddr(ip) in a thread (3s timeout).
Corporate hostnames ("vpn.acmecorp.com", "fw.company.net") → extract domain.

Filters:
  _PTR_RESIDENTIAL_RE: rejects broad/dsl/cable/dhcp/pool/customer patterns
  _CDN_INFRA_DOMAINS:  rejects cloudfront.net, a-msedge.net, 1e100.net etc.
  is_isp_or_cloud():   rejects if ISP keyword in org name

_CDN_DOMAIN_TO_COMPANY: Maps CDN domains to parent companies
  ("a-msedge.net" → ("Microsoft", "microsoft.com"))

_PTR_CORPORATE_RE: boosts confidence if hostname contains vpn/proxy/corp/egress.
Sets confidence 0.55 (corporate keyword match) or 0.35 (plain domain from PTR).

────────────────────────────────────────────────────────────────────────────────
STEP 0: ip-api.com (FREE)
────────────────────────────────────────────────────────────────────────────────
GET http://ip-api.com/json/{ip}?fields=...
Returns: city, region, country, ISP (org), AS number, query, mobile, proxy, hosting

Key logic:
  - ASN cache: Redis key asn:{asnum} TTL=24h → skip API for repeat corporate ASNs
  - If `org` field is corporate (not ISP): sets company + confidence 0.6
  - If `proxy`=true or `hosting`=true: sets tier="noise"
  - Builds geo dict: {city, region, country, isp, mobile, proxy, as_num}
  - Mobile flag: sets `is_mobile=true` in resolution (mobile users rarely corp)

Note: ip-api.com free tier is HTTP-only, rate limited at 45 req/min.

────────────────────────────────────────────────────────────────────────────────
STEP 1: IPINFO (PAID PLAN)
────────────────────────────────────────────────────────────────────────────────
ipinfo SDK: handler.getDetails(ip) async
Returns: city, region, country, org (AS name), company.name, company.domain,
         company.type (business/isp/education/hosting/government)

Only sets company+domain when company.type == "business".
Skips if type is isp/hosting/education. Sets confidence 0.65 on company hit.

────────────────────────────────────────────────────────────────────────────────
STEP 2: ENRICH.SO IP LOOKUP
────────────────────────────────────────────────────────────────────────────────
POST https://api.enrich.so/v1/person-ip or GET /company-ip
Returns: company name, domain, employee_count, industry, location

Applies _normalize_company_name() before storing.
Sets confidence 0.70 on company hit.
Domain validation: skips personal email domains.

────────────────────────────────────────────────────────────────────────────────
STEP 2.5: MX VALIDATION (FREE — DNS)
────────────────────────────────────────────────────────────────────────────────
dns.resolver.resolve(domain, "MX") with 3s timeout.
Only runs if confidence < 0.65 (domains already confirmed by Explorium don't need it).

  - No MX records: sets _mx_unverified=True, caps confidence at 0.35
    (likely a reverse-DNS hostname, not a real corporate email domain)
  - MX records found: confirms corporate domain, boosts confidence to 0.55

────────────────────────────────────────────────────────────────────────────────
REDIS DOMAIN CACHE CHECK
────────────────────────────────────────────────────────────────────────────────
Key: enrich:domain:{domain}  TTL: 6 hours
Merges: company, explorium, logo_url, decision_makers, employees from cache.
Sets confidence=0.65. Skips steps 3–5.6 if cache hit.

────────────────────────────────────────────────────────────────────────────────
STEP 3: ENRICH.SO EMAIL PERSON LOOKUP (email path only)
────────────────────────────────────────────────────────────────────────────────
Only runs if email was form-captured (pixel identify() or form submit).
POST https://api.enrich.so/v1/person?email={email}
Returns: full_name, phone, linkedin_url, job_title, company, company_domain

Populates resolution person dict. Company from email domain sets confidence 0.75.

────────────────────────────────────────────────────────────────────────────────
STEP 3b: BETTERCONTACT (email path)
────────────────────────────────────────────────────────────────────────────────
Async waterfall enrich for email → phone, LinkedIn, job_title.
Falls back gracefully if no API key configured.

────────────────────────────────────────────────────────────────────────────────
STEP 3c: CONTACTOUT EMAIL (email path)
────────────────────────────────────────────────────────────────────────────────
ContactOut person lookup by email → LinkedIn profile, phone, current company.

────────────────────────────────────────────────────────────────────────────────
STEP 4: CONTACTOUT DM (domain path)
────────────────────────────────────────────────────────────────────────────────
Only runs if domain is known. Fetches top decision-makers at that company.
Stores in resolution["decision_makers"] as [{name, email, title, linkedin}].
Used by dashboard to show "You should talk to: [Name, VP Sales]".

────────────────────────────────────────────────────────────────────────────────
STEP 5: EXPLORIUM FULL ENRICHMENT (3 phases)
────────────────────────────────────────────────────────────────────────────────
The single most data-rich step. Uses the full Explorium B2B graph.

Phase 1 — MATCH:
  search_companies({domain} or {name}) → internally calls:
    POST /businesses/match with [{domain, name}]
    → business_id (Explorium's internal stable identifier)
    → fetch_businesses({business_id}) for full basic profile
    → normalize_company() → {name, domain, industry, employee_count_range,
       employee_count_exact, revenue_range, logo_url, linkedin_url, headquarters...}

  Name ranking: scores candidates by similarity to query name/domain.
  Excludes mega-brands (google.com, amazon.com) from name-only queries.
  confidence_bump = 0.9 (domain match) or 0.8 (name match)

Phase 2 — enrich_company_fully(matched_company):
  Runs 4 sequential Explorium module calls:
  a. POST /businesses/firmographics/enrich (business_id)
     → naics, sic, industry, employee_count_range, revenue_range, revenue_exact,
       logo_url, company_type, HQ city/state/country/zip, linkedin_industry_category
  b. POST /businesses/funding_and_acquisition/enrich (business_id)
     → investors[], funding_total, last_funding_date, funding_stage
  c. POST /businesses/financial_indicators/enrich (business_id)
     → revenue_exact (yearly), peer_companies (competitors)
  d. POST /businesses/technographics/enrich (business_id)
     → full_tech_stack[] (programming languages, frameworks, cloud, databases, etc.)

Phase 3 — LinkedIn Posts:
  POST /businesses/linkedin_posts/enrich (business_id)
  → posts[] (last 10), followers count
  Stored as resolution["explorium"]["linkedin_posts"],
             resolution["explorium"]["linkedin_followers"]

Propagates to top-level:
  resolution["company"]       ← Explorium always wins on name
  resolution["domain"]        ← canonical registered domain (if not set)
  resolution["linkedin_url"]  ← company LinkedIn URL
  resolution["logo_url"]      ← company logo
  resolution["tech_stack"]    ← list of tech names (max 30)

────────────────────────────────────────────────────────────────────────────────
STEP 5b: HUNTER.IO (domain path, if no person yet)
────────────────────────────────────────────────────────────────────────────────
GET https://api.hunter.io/v2/domain-search?domain={domain}&limit=5
Returns: first/last name, email pattern, seniority, department for top contacts.
Only runs if no full_name + email already in resolution.

────────────────────────────────────────────────────────────────────────────────
STEP 5c: CLEARBIT COMPANY (fallback)
────────────────────────────────────────────────────────────────────────────────
GET https://company-stream.clearbit.com/v2/companies/domain={domain}
Returns: description, employee_count, revenue_range, industry, logo.
Only fills fields not already set. Low-priority fallback if Explorium missed.

────────────────────────────────────────────────────────────────────────────────
STEP 5.5: IP RDAP (FREE)
────────────────────────────────────────────────────────────────────────────────
GET https://rdap.org/ip/{ip}
Returns: network name, registrant org from IP block record.
Only runs if confidence < 0.60. Free, no API key.
Sets confidence 0.50 on company hit.

────────────────────────────────────────────────────────────────────────────────
STEP 5.6: DOMAIN RDAP (FREE)
────────────────────────────────────────────────────────────────────────────────
GET https://rdap.org/domain/{domain}
Extracts registrant org from domain's vCard "fn" or "org" property.
More authoritative than IP RDAP — domain registrant IS the company.
Only runs if domain known AND not _mx_unverified.
Sets confidence 0.65 on company hit.

────────────────────────────────────────────────────────────────────────────────
STEP 7: MULTI-SOURCE AGREEMENT BOOSTER
────────────────────────────────────────────────────────────────────────────────
Collects normalised company names from 7 sources:
  ipapi_org, ptr_company, ipinfo_company, enrich_so_company,
  rdap_company, domain_rdap_company, explorium_company

Applies _normalize_company_name() to each (strips Ltd/Inc/LLC/GmbH etc.)
Counts occurrences:
  - 3+ sources agree → confidence = max(current, 0.90)
  - 2 sources agree  → confidence = max(current, 0.78)
  Uses the most-agreed-upon name as the canonical company.

────────────────────────────────────────────────────────────────────────────────
STEP 8: IDENTITY GRAPH STORE
────────────────────────────────────────────────────────────────────────────────
Upserts identity_node with:
  visitor_id, ip, email, full_name, company_name, company_domain,
  phone, linkedin_url, job_title
  raw_data = {"fingerprint": fp_hash, ...}

TIERING (applied after all steps):
  "noise"   — bot_score ≥ 40, OR company is an ISP/cloud/residential provider
  "person"  — confidence ≥ 0.65 AND (email OR person data known)
  "company" — company or domain known (even if no person)
  "unknown" — nothing identified


================================================================================
 6. BEHAVIORAL INTELLIGENCE ENGINE
================================================================================

Triggered per visit in _process_visitor_data() after enrichment.
Reads last 30 visits for this visitor_id from DB.

SIGNAL DIMENSIONS:
  1. Page Topic Taxonomy   — URL path segments → weighted persona scores
     130+ keywords mapped to 7 personas: engineering / sales / executive /
     marketing / hr / product / finance
     Fuzzy match: substring matching at 0.6× weight

  2. Page Meta Signals     — page <title> + <h1> text (pixel.js v2.2)
     12 regex patterns: pricing, api, enterprise, integration, roi, careers,
     analytics, marketing, product, case-study, demo, finance
     Worth 70% of URL signal weight

  3. Dwell Time Weighting  — longer time on page amplifies topic signal
     <5s: noise (weight 0.3), 5-30s: 0.6, 30s-2min: 0.9, >2min: 1.2

  4. Scroll Depth          — deep scroll = genuine interest (>70%: +8 pts)

  5. CTA Click Tracking    — clicks on pricing/demo/signup buttons (+15 pts)

  6. Visit Frequency       — repeat visitors: +5 per additional visit (cap 15)

  7. Session Depth         — pages per session: 3+: +5, 5+: +10, 10+: +15

  8. Form Interaction      — email submitted on any visit: +20 pts engagement

  9. Referrer Signals      — linkedin.com → executive/sales/hr, github → engineering
     g2.com / capterra / trustradius → sales/product (review site = active eval)

  10. Time-of-Day          — business hours (8am–6pm UTC): +3 pts
      Early AM / late PM: small negative (often bots or non-decision-makers)

  11. UTM Signals          — utm_content/campaign/term classified against 7 patterns

  12. Visit Velocity       — pages/hour in last 10 visits (cap 20 ph)
      >5 ph: +3 pts, >10 ph: +5 pts (active research mode)

  13. Engagement Decay     — exponential decay with 14-day half-life
      Days since last visit → score × 0.5^(days/14), minimum 1

JOB TITLE OVERRIDE:
  If job_title is known (from email enrichment), maps directly to persona.
  180+ title→persona mappings: CTO→engineering, VP Sales→sales, CEO→executive etc.

BUYING STAGE CLASSIFICATION:
  "decision":     CTA clicks ≥ 2, OR engagement ≥ 75, OR pricing page visited,
                  OR demo page visited
  "consideration": engagement ≥ 45 OR (scroll >50% AND visited features/solutions)
  "awareness":     default (browsing, early research)

OUTPUT: {predicted_persona, engagement_score (0-100), buying_stage,
         persona_confidence (0.0-1.0), signals_breakdown}


================================================================================
 7. IDENTITY GRAPH & CROSS-ORG MATCHING
================================================================================

The identity graph solves the hardest problem in visitor tracking: the same
physical person visits multiple unrelated customer sites, using the same browser.

STORAGE: identity_nodes table (one row per identified visitor per org context)

LOOKUP CASCADE (5 levels, most → least specific):
  1. visitor_id exact: same localStorage UUID → definitive match
  2. Fingerprint cross-org: expression index on raw_data->>'fingerprint'
     Same cyrb53 hash seen from any org's pixel → re-identified instantly
  3. /24 subnet: all IPs in same /24 block share company data
     Handles corporate NAT where entire office uses one public IP range
  4. Exact IP: single IP match (works for static office IPs)
  5. Email: if email provided → look up prior enriched data

STORAGE (after enrichment):
  Stores fingerprint hash in raw_data JSONB.
  Expression index: ON identity_nodes ((raw_data->>'fingerprint'))
  WHERE raw_data->>'fingerprint' IS NOT NULL
  → O(log n) lookup for cross-org re-identification

RETROACTIVE BACKFILL:
  When visitor submits email for first time, patches ALL prior anonymous visits:
  email, full_name, company, domain, job_title, linkedin_url, logo_url
  Uses dynamic JSONB jsonb_set chain to update each column atomically.

/24 SUBNET LIMITATION:
  Returns company-level data only (not personal) when matched via /24 subnet.
  Prevents incorrectly attributing one employee's identity to another.


================================================================================
 8. COMPANY-LEVEL ACCURACY TECHNIQUES
================================================================================

Seven-source agreement architecture (no single point of failure):

  Source             Type    Cost      Confidence    Coverage
  ─────────────────────────────────────────────────────────────────────────
  PTR Reverse DNS    Free    $0        0.35–0.55     ~30% B2B traffic
  ip-api.com         Free    $0        0.50–0.60     ~60% (has ISP noise)
  IPinfo             Paid    Low       0.60–0.65     ~55% business IPs
  Enrich.so          Paid    Medium    0.65–0.70     ~45% B2B IPs
  Explorium Match    Paid    High      0.80–0.90     ~80% when domain known
  IP RDAP            Free    $0        0.45–0.50     ~35% (public IPs only)
  Domain RDAP        Free    $0        0.60–0.65     ~50% (when domain known)
  ─────────────────────────────────────────────────────────────────────────

ASN Cache (Redis, 24h TTL):
  Corporate ASNs (e.g. APPLE-ENGINEERING, GOOGLE-CORP-NET) are cached.
  Repeat visitors from same corporate ASN get instant identification.

ISP/Cloud Filter (ISP_CLOUD_KEYWORDS):
  ~200+ keywords covering major ISPs in India, US, UK, EU, Canada, Australia.
  Prevents residential/mobile IPs from being labelled as companies.
  Per-org isp_allowlist can exempt specific ISPs (for ISP-employed prospects).

_normalize_company_name():
  Strips legal suffixes: Ltd, Inc, LLC, GmbH, Pvt Ltd, Pte Ltd, S.A., S.R.L. etc.
  Rejects junk names: "Inc", "Holdings", "Technologies", "Solutions" etc.
  Allows multi-source agreement booster to work correctly across APIs.

CDN Domain Mapping:

20. DEEP ANALYSIS: PROS, CONS, LIMITATIONS & ACCURACY ASSESSMENT
================================================================================

────────────────────────────────────────────────────────────────────────────────
PROS — WHAT WORKS WELL
────────────────────────────────────────────────────────────────────────────────

P1. MULTI-SOURCE WATERFALL ARCHITECTURE
    Seven independent enrichment sources with confidence scoring means no single
    API failure kills identification. PTR → ip-api → IPinfo → Enrich.so → Explorium
    → RDAP cascade ensures maximum coverage. If Explorium is down, RDAP still works.

P2. CROSS-ORG BROWSER FINGERPRINT IDENTITY
    The most powerful feature: cyrb53 fingerprint stored across ALL orgs means a
    visitor who was identified on client A's site (e.g. via email form) is instantly
    identified when they visit client B's site — at zero additional API cost.
    Expression index ensures this is O(log n) even at millions of nodes.

P3. /24 SUBNET CORPORATE NAT HANDLING
    Correctly handles the fact that most corporate offices have a single public IP
    or a /24 block. When we've identified Acme Corp from 10.20.30.X, all subsequent
    visits from 10.20.30.* get the company identity instantly.

P4. DEEP ISP FILTER (~200 KEYWORDS)
    Comprehensive ISP_CLOUD_KEYWORDS list covering India, US, UK, EU, Canada,
    Australia, Asia, LATAM. Prevents residential/mobile IPs from polluting the
    dashboard with Jio/Comcast/BT labelled as "companies".
    Per-org isp_allowlist for edge cases (e.g. customers in ISP industry).

P5. RETROACTIVE BACKFILL ON EMAIL CAPTURE
    When a visitor finally submits a form, all their prior anonymous visits are
    retroactively patched with full identity. This turns a history of "unknown"
    visits into a rich B2B account timeline — a key differentiator vs competitors.

P6. FULL EXPLORIUM FIRMOGRAPHIC DEPTH
    Single Explorium match unlocks: industry, employee count (exact AND range),
    revenue (exact AND range), funding stage, investors, tech stack, LinkedIn URL,
    company logo, HQ location, company type. No other competitor provides this
    richness from a single matched IP → company identity.

P7. FULL CONSENT COMPLIANCE (PIXEL v2.2)
    Synchronous DNT + GPC + Cookiebot + OneTrust checks at script load.
    Async TCF 2.0 deferred consent (IAB framework).
    Mid-session revocation: _isConsentDenied() checked on every track() call.
    optOut() / optIn() public API for manual user control.
    Server-side opt-out stored in Redis (persists across devices).

P8. BEHAVIORAL SCORING DEPTH
    13 signal dimensions including page meta (title/h1), velocity (pages/hour),
    engagement decay (14-day half-life), UTM signals, referrer persona affinity.
    180+ job title→persona mappings for direct role identification.
    Buying stage (awareness/consideration/decision) for CRM prioritisation.

P9. REDIS ARCHITECTURE (RATE LIMITING + DEDUP + SSE + CACHE)
    Single Redis instance powers 5 distinct features: rate limiting, dedup,
    domain enrichment cache, SSE PubSub channel, SSE exchange tokens.
    Keepalive loop (45s ping) prevents Upstash idle connection resets.
    reset() now reconnects immediately (not on next request) — avoids double-fail.

P10. ICP SCORING SYSTEM
     Per-org configurable weights (w_company, w_person, w_industry etc.).
     Industry match bonus/penalty, employee count range filtering.
     Allows different orgs to define their own ideal customer profile for
     prioritised routing: high ICP scores surfaced prominently in dashboard.


────────────────────────────────────────────────────────────────────────────────
CONS & LIMITATIONS
────────────────────────────────────────────────────────────────────────────────

C1. ENRICHMENT PIPELINE IS FULLY SEQUENTIAL (CRITICAL PERFORMANCE ISSUE)
    PROBLEM: All 12+ enrichment steps run in serial await chains. A single slow
    API (Explorium timeout = 15s) blocks the entire pipeline. Total enrichment
    time can reach 30–60 seconds for cold cache hits with all APIs called.
    IMPACT: Dashboard shows "processing" spinner for a long time. Late-arriving
    data is less actionable. High API latency degrades UX significantly.
    ROOT CAUSE: Each step modifies the shared `resolution` dict, making simple
    parallelisation unsafe without explicit dependency ordering.

C2. NEW VisitorEnricher() CREATED PER TASK (MEMORY + LATENCY)
    PROBLEM: Every Celery task instantiates a new VisitorEnricher(), which creates
    a new ExploriumService(), BetterContactService(), ContactOutService(),
    FullContactService(), EmployeeDiscoveryService(). Each has its own API key
    validation and print statements at init time.
    IMPACT: Wasted memory allocation per task. Debug print() statements run on
    every enrichment (visible in prod logs). No connection reuse across tasks.

C3. ip-api.com FREE TIER: HTTP + RATE LIMIT
    PROBLEM: ip-api.com free tier is HTTP-only (no HTTPS) and limited to 45 req/min.
    At high traffic (>45 concurrent enrichments/min), requests begin failing.
    HTTP also means the ASN/org data is visible in network transit.
    IMPACT: Geo accuracy degrades under load. No company data when rate-limited.

C4. DOMAIN CACHE STORES EVERYTHING INCLUDING EXPLORIUM MODULES
    PROBLEM: The 6-hour domain cache stores the ENTIRE resolution dict including
    Explorium firmographics, technographics, LinkedIn posts. The cache key is just
    the domain. If Explorium returns stale/wrong data (e.g. wrong employee count),
    that error propagates to ALL visitors from that company for 6 hours.
    IMPACT: Stale enrichment data served for hours. No TTL stratification
    (fresh Explorium data expires at the same rate as PTR DNS data).

C5. EXPLORIUM enrich_company_fully() IS SEQUENTIAL INSIDE THE STEP
    PROBLEM: Phase 2 of _step_explorium calls enrich_company_fully() which runs
    firmographics → funding → financial_indicators → technographics in sequence.
    4 sequential Explorium API calls at ~500ms each = ~2s minimum.
    LinkedIn posts is a 5th call (Phase 3). Total Explorium latency: ~2.5–4s.
    IMPACT: Explorium is already the slowest step; sequential modules make it worse.

C6. NO COMPANY DEDUPLICATION ACROSS VISITS IN REAL-TIME
    PROBLEM: The same company (e.g. "Tata Consultancy Services") can appear in
    the visits table under multiple name variants: "TCS", "Tata Consultancy",
    "Tata Consultancy Services Limited", "TATA CONSULTANCY SERVICES".
    _normalize_company_name() helps for agreement detection but the stored
    resolution["company"] field may still have inconsistencies.
    IMPACT: Dashboard shows the same company 3+ times with different names.
    Account-level aggregation in /accounts endpoint may split data incorrectly.

C7. BEHAVIORAL SCORING RUNS ON LAST 30 VISITS — NO LONGER WINDOW
    PROBLEM: predict_persona() only queries last 30 visits. Power users who have
    visited 100+ times have their early signals ignored.
    The 14-day engagement decay correctly handles staleness, but a very engaged
    visitor who made 50 visits last week before this sprint would have their
    first 20 visits completely invisible to the scoring engine.
    IMPACT: Underestimated engagement for high-frequency visitors. Buying stage
    "decision" may not be triggered for visitors who already have strong signals
    in visit #31+.

C8. BOT DETECTION IS BASIC
    PROBLEM: Bot filtering only checks UA strings (bot/crawler/spider/headless),
    viewport 0, and webdriver/Phantom flags at pixel.js level. Headless browsers
    with random UAs, realistic viewports, and no webdriver flag pass through.
    Playwright/Puppeteer bots with realistic fingerprints are not caught.
    IMPACT: Sophisticated crawlers and monitoring tools inflate visit counts.
    Bot_score from the server-side is capped at 50 max before enrichment, so
    some borderline bots get through as company-level visits.

C9. PRIVATE IP RETURNS INSTANTLY WITH NO DATA
    PROBLEM: Private IP detection (127.x, 10.x, 192.168.x, 172.16–31.x) returns
    early with empty geo and no enrichment. In local development/testing, this
    means no data is visible in the dashboard.
    The IPv6 private range (::1) is checked but other IPv6 private ranges (fc00::/7)
    are NOT checked. IPv6 ULA addresses (fc00:: to fdff::) could sneak through.
    IMPACT: Incomplete IPv6 handling. May cause unnecessary enrichment attempts
    for IPv6 addresses that are actually private/link-local.

C10. NO FALLBACK WHEN CELERY IS UNAVAILABLE
     PROBLEM: When Celery is down, the code falls back to asyncio.create_task()
     for inline processing. But asyncio.create_task() in a FastAPI request handler
     context doesn't guarantee the task completes if the process restarts.
     The task may be lost silently if the server shuts down mid-enrichment.
     IMPACT: Visit data loss during Celery outages. No dead-letter queue for
     failed enrichments. No visibility into how many visits were lost.

C11. VISITOR_DEDUPE_SECONDS USES SAME TTL FOR ALL ORGS
     PROBLEM: VISITOR_DEDUPE_SECONDS is a single global setting. High-traffic orgs
     need shorter dedup windows (to catch multiple visits from the same company on
     different pages), while low-traffic orgs benefit from longer dedup windows.
     The fingerprint dedup window (4× normal) is hardcoded, not configurable.
     IMPACT: Under-counting at high traffic or over-counting at low traffic
     depending on the global setting value.

C12. THE IDENTITY GRAPH IS ONLY CHECKED ON COLD CACHE MISSES
     PROBLEM: Identity graph lookup (Step -1) runs BEFORE the domain cache check.
     But the domain cache check at Step 2.5 completely skips steps 3–5.6 including
     the identity graph store (step 8). This means:
     - If domain is cached: identity graph is still read (correct) but NOT updated.
     - New person data (email capture) won't propagate to identity_nodes
       if the domain was recently cached.
     IMPACT: Identity graph can become stale for frequently-visited domains.
     Cross-org fingerprint matching may miss updates for high-traffic companies.

C13. CLEARBIT LOGO API USED AS FALLBACK FOR LOGO_URL
     PROBLEM: resolution["logo_url"] falls back to:
     f"https://logo.clearbit.com/{domain}" for ALL visits without a logo.
     This is an undocumented Clearbit endpoint that may have rate limits and
     no SLA. Clearbit was acquired by HubSpot (2022) and the free logo API
     could be deprecated at any time.
     IMPACT: Logo images could break for all visitors if Clearbit removes this
     free endpoint. No fallback (gravatar, favicon, etc.).

C14. ENRICHMENT STEPS HAVE NO INDIVIDUAL TIMEOUTS
     PROBLEM: Each enrichment step's httpx.AsyncClient has a global timeout of
     15s (connect=5s). There is no step-level timeout budget. A slow RDAP server
     or unresponsive Clearbit can hold the pipeline for 15 full seconds at that
     one step.
     IMPACT: Tail-latency on enrichment can be 60s+ if 4 APIs each timeout.
     No circuit breaker to skip consistently-failing APIs after N failures.

C15. NO WEBHOOK SIGNATURE VERIFICATION EXAMPLE IN DOCS
     PROBLEM: The system generates HMAC-SHA256 signatures via X-Outmate-Signature
     but there is no customer-facing documentation or SDK code for verifying the
     signature in webhook receivers.
     The Alert table tracks delivery status but the customer has no dashboard
     view of webhook delivery health or failure logs.

C16. DEDUP DOES NOT HANDLE SAME COMPANY DIFFERENT IPs
     PROBLEM: The Redis deduplication key is:
     visits:{org_id}:{ip}:{domain}   (IP-based dedup)
     visits:{org_id}:fp:{fp}         (fingerprint dedup)
     If the same company employee visits from two different IPs (e.g. office WiFi
     and mobile hotspot) within the dedup window, they create two separate visit
     records, even if the /24 subnet later identifies both as same company.
     IMPACT: Inflated visit counts for large companies with multiple egress IPs.
     Account-level intent score may be artificially high due to double-counting.

C17. ACCOUNT-LEVEL INTENT CACHE IS 2 HOURS STALE
     PROBLEM: aggregate_account_intent_task caches results for 2h in Redis.
     The /accounts API endpoint reads from this cache. If a company has a burst
     of high-intent visits in the last 10 minutes, the accounts endpoint won't
     reflect this for up to 2 hours.
     IMPACT: /accounts endpoint is unsuitable for real-time sales triggers.
     The dashboard SSE stream shows individual visits in real-time, but the
     aggregate account view is always behind.

C18. PIXEL.JS FINGERPRINT HAS CANVAS FINGERPRINT BLOCKING RISK
     PROBLEM: canvas.toDataURL() fingerprinting is blocked by Firefox's
     "Enhanced Tracking Protection" (Strict mode) and Brave Browser's
     fingerprint randomisation. When canvas returns a blank or random result,
     the fingerprint changes on every page load.
     IMPACT: Cross-session identity breaks for ~15-20% of privacy-conscious users.
     Multiple identity_nodes are created for the same physical person.
     /24 subnet fallback partially mitigates this for corporate IPs.

C19. THE enrich_ip() RUNS EVERY CALL — NO PERSON-LEVEL CACHE
     PROBLEM: Domain-level results are cached for 6h, but person-level enrichment
     (Enrich.so email, BetterContact, ContactOut) runs every time an email is
     seen, even if that exact email was enriched 2 hours ago.
     IMPACT: Unnecessary API credits spent re-enriching the same email addresses.
     No email→person cache in Redis. Costs scale linearly with email volume.

C20. SSE STREAM HAS NO BACKFILL MECHANISM
     PROBLEM: When a user opens the dashboard, they connect to the SSE stream
     for live updates. But any visits that were enriched BETWEEN the last page
     refresh and the SSE connection moment are missed.
     The initial GET /visitors?limit=50 fetch covers this partially, but there
     is a race window where a visit can be processed, published to Redis PubSub,
     and consumed by no subscriber — then the user opens the page and sees nothing.
     IMPACT: "I just visited my own website but don't see myself in the dashboard"
     user confusion. Requires a manual refresh to see visits from the gap window.

ACCURACY ASSESSMENT: REALISTIC IDENTIFICATION RATES
================================================================================

Traffic type breakdown (typical B2B SaaS website):

  ~40% of raw visits: Bots/crawlers/monitoring → filtered by bot pre-check
  ~15% of real visits: Consumer ISP / mobile → filtered by ISP_CLOUD_KEYWORDS
  ~5% of real visits: VPN / Tor / proxy → filtered (proxy=true from ip-api)
  ──────────────────────────────────────────────────────��──────────────────
  ~40% of raw visits reach enrichment pipeline

Of the ~40% that reach enrichment:
  ~70% get company-level identification (tier="company" or "person")
  ~30% remain unknown (residential ISPs not in filter list, new cloud IPs)

  Of the ~70% identified:
    ~55% via ip-api.com org field (first, cheapest source)
    ~20% incremental from Explorium match (adds firmographic richness)
    ~15% incremental from PTR + RDAP + Domain RDAP (long tail)
    ~10% remain unidentified despite multiple sources

  ~8% of all visits get person-level identification (tier="person")
  These are form-captured emails + retroactive backfill.

EFFECTIVE IDENTIFICATION RATE vs COMPETITORS:
  rb2b:      claims ~20-40% B2B company match rate
  warmly.ai: claims ~15-35% B2B company match rate
  Outmate:   ~28% of all raw traffic = company identified (≈40% of real B2B traffic)
  Key advantage: retroactive backfill + Explorium depth + cross-org fingerprint

WHERE IDENTIFICATION FAILS:
  1. Home workers on consumer ISPs (post-COVID: ~35% of remote workforce)
  2. VPN/Zerotier/corporate proxy users (IP = proxy IP, not office IP)
  3. Mobile users (cellular IP → assigned to carrier, not company)
  4. Cloud/AWS users (browsing from EC2 → AWS org, not company)
  5. ISPs not in our filter list → labelled as "company" incorrectly
  6. Domain privacy registrars → RDAP returns "Domains by Proxy, LLC" not company
  7. Companies without PTR records or clean ASN assignments (small businesses)
